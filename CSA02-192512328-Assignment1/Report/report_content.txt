1. INTRODUCTION

Electricity billing is an important process for electricity co-operatives because the amount charged to each consumer must be calculated accurately from the electricity consumed. A reliable billing program must apply the correct tariff rates, include the fixed charge, and handle unusual situations such as meter rollover and invalid user input.

This assignment develops a C programming solution for a rural electricity co-operative. It demonstrates the use of data types, constants, preprocessor directives, input/output functions, type conversion, compilation stages, and testing. Monetary values are represented using integer paise to support accurate billing calculations.

The assignment also examines the design of a smart meter system that records electricity usage every 15 minutes and applies a higher tariff during specified peak hours.

2. PROBLEM STATEMENT

The objective is to design, implement, and validate an electricity billing program that calculates a consumer's bill using meter readings and the specified tariff structure.

The billing rules are:

Fixed charge: ₹50.

The assignment also requires consideration of data type ranges, macro safety, compilation stages, testing, computational complexity, and the design of a smart meter system with configurable time-of-day tariffs.

4. PROBLEM ANALYSIS

4.1 Inputs

The main inputs to the billing system are the previous meter reading and the current meter reading. Each reading belongs to a 16-bit unsigned meter register with values from 0 to 65535.

For the interactive billing program, the number of electricity units consumed may also be entered directly. The smart meter extension additionally uses time-stamped energy readings and tariff configuration values.

4.2 Processing

The system calculates electricity consumption from the meter readings and accounts for register rollover. It then applies the tariff rules and adds the fixed charge of ₹50.

The first 100 units have no energy charge. Units from 101 to 200 are charged at ₹2.25 per unit, and units above 200 are charged at ₹4.50 per unit.

Monetary calculations are performed in integer paise. Input validation is required to detect invalid values and prevent incorrect calculations.

4.3 Outputs

The program displays the electricity units consumed, the calculated bill, and relevant error messages when input is invalid. The test programs also display data type sizes, numeric ranges, and compilation or calculation results where required.

4.4 Alternative Representation of Meter Readings

Meter readings can be stored as integers or as strings.

Integer representation allows arithmetic operations to be performed directly. For a fixed-width register, consumption calculation requires a constant number of operations, giving O(1) time complexity and O(1) additional space complexity.

String representation stores the reading as characters. The string must be validated and converted to a numeric value before arithmetic can be performed. Conversion and validation may require O(d) time, where d is the number of digits in the reading.

For this assignment, integer representation is more suitable because the meter readings are numeric and must be used in arithmetic calculations.

5. DATA TYPES AND DATA REPRESENTATION

Selecting suitable data types is important for reliable electricity billing. The selected type must support the required numeric range and the operations performed by the program.

5.1 Meter Readings

The program uses unsigned short as the meter reading type. It stores non-negative values and is suitable for the 16-bit meter register when the implementation supports the range 0 to 65535.

The program checks the maximum value using USHRT_MAX. C does not guarantee that unsigned short is exactly 16 bits on every platform, so the size and range should be verified.

5.2 Electricity Consumption

Unsigned integer types are suitable for representing non-negative electricity consumption. The program uses arithmetic to calculate consumption and handle meter rollover.

5.3 Monetary Values

The billing program stores monetary values as integer paise. For example, ₹50 is represented as 5000 paise, and ₹162.50 is represented as 16250 paise.

This representation avoids floating-point rounding errors in the storage and arithmetic of amounts expressed in whole paise.

5.4 Large Accumulated Totals

The long and long long types are used to demonstrate larger integer ranges and accumulated billing totals. The actual range of each type depends on the C implementation and should be checked using the appropriate limits.

5.5 Floating-Point Types

The float and double types are used to demonstrate floating-point precision. They are useful for many real-number calculations, but decimal monetary values may not have exact binary representations. Integer paise is therefore preferred for the billing calculations in this assignment.

7. PROGRAM DESIGN AND ALGORITHMS

7.1 Meter Consumption Algorithm

Step 1: Read the previous and current meter readings.
Step 2: Validate that both readings are within the supported meter range.
Step 3: If the current reading is greater than or equal to the previous reading, calculate consumption by subtracting the previous reading from the current reading.
Step 4: If the current reading is smaller than the previous reading, treat it as a possible meter rollover and calculate consumption using the 16-bit register range.
Step 5: Display the calculated consumption.

For a 16-bit unsigned meter register, the number of possible register values is 65536. Therefore, the rollover calculation must account for the range from 0 to 65535.

7.2 Billing Algorithm

Step 1: Read the electricity consumption in units.
Step 2: Validate the input and reject negative or invalid values.
Step 3: Start the energy charge at zero.
Step 4: The first 100 units have no energy charge.
Step 5: Charge 225 paise per unit for units from 101 through 200.
Step 6: Charge 450 paise per unit for units above 200.
Step 7: Add the fixed charge of 5000 paise.
Step 8: Display the final bill in rupees and paise.

7.3 Billing Formula

For consumption U units, the energy charge in paise is calculated as follows:

If U is less than or equal to 100:

Energy charge = 0

If U is greater than 100 and less than or equal to 200:

Energy charge = (U - 100) × 225

If U is greater than 200:

Energy charge = (100 × 225) + ((U - 200) × 450)

Total bill in paise = Energy charge + 5000

The final amount is converted to rupees for display. The program performs the monetary calculations using integer paise.

10. COMPILATION STAGES

The C programs were compiled using GCC. Compilation converts human-readable source code into an executable program through several stages.

10.1 Preprocessing

The preprocessor handles directives such as #include, #define, and conditional compilation. The preprocessed source file was generated using:

gcc -E main.c -o main.i

10.2 Compilation to Assembly

The preprocessed source was translated into assembly language using:

gcc -S main.i -o main.s

10.3 Assembly

The assembly source was converted into an object file using:

gcc -c main.s -o main.o

10.4 Linking

The object file was linked to produce an executable program using:

gcc main.o -o main

10.5 Execution

The executable was run to verify the program output. Warning options such as -Wall and -Wextra can be used during compilation to help identify potential problems.

These stages demonstrate how a C program progresses from source code to an executable file.

11. COMPLEXITY ANALYSIS

Time complexity describes how the execution time grows as the input size increases. Space complexity describes the additional memory required by an algorithm.

11.1 Meter Consumption Calculation

The consumption calculation uses a fixed number of arithmetic operations and comparisons. Its time complexity is O(1), and its auxiliary space complexity is O(1).

11.2 Billing Calculation

The billing calculation checks the applicable tariff slab and performs a fixed number of arithmetic operations. Its time complexity is O(1), and its auxiliary space complexity is O(1).

11.3 Input Validation

For a single numeric input, validation uses a fixed number of checks. Its time complexity is O(1), and its auxiliary space complexity is O(1).

If a program processes multiple input readings, the total processing time grows with the number of readings. Processing n readings individually takes O(n) time.

11.4 Smart Meter Data Processing

The smart meter challenge involves 35,040 readings per house per year when one reading is recorded every 15 minutes.

Processing all annual readings once takes O(n) time, where n is the number of readings. Storing all readings requires O(n) space if they are retained in memory. A streaming design can process readings incrementally and use less working memory, while persistent storage is used to retain the records.

12. INTEGER AND FLOATING-POINT ACCURACY

12.1 Integer Arithmetic for Billing

The billing program represents monetary amounts in integer paise. This avoids floating-point rounding errors during the tariff calculations.

For example, ₹162.50 is represented as 16250 paise. The final amount is displayed in rupees and paise by dividing the integer amount by 100 and displaying the remainder as two decimal digits.

12.2 Floating-Point Representation

The assignment demonstrates the use of float and double for real-number calculations. Some decimal fractions cannot be represented exactly in binary floating-point format. Therefore, repeated floating-point calculations may introduce small rounding differences.

Integer paise is preferred for the billing calculations because the tariff rates and final monetary amounts can be represented as whole paise.

12.3 Numeric Range and Overflow

The range of a data type depends on its implementation. The program uses limits.h and float.h to examine numeric limits.

Large accumulated totals require a sufficiently wide integer type. The program must also ensure that intermediate calculations do not overflow. Production software should validate maximum consumption values and use a data type that can safely represent the largest possible bill.

13. SMART METER DESIGN CHALLENGE

13.1 Reading Frequency

The proposed smart meter system records electricity readings every 15 minutes.

There are four readings per hour and 96 readings per day. For a 365-day year, the total number of readings per house is:

96 × 365 = 35,040 readings per year.

13.2 Peak-Hour Tariff

The system identifies readings recorded between 6 PM and 10 PM as peak-hour readings. The proposed peak-hour tariff is 20% higher than the applicable normal tariff.

Each reading must have a timestamp so that the system can identify the correct tariff period. The exact treatment of consumption across tariff periods must be defined by the billing policy.

13.3 Runtime Tariff Configuration

Tariff values should be stored in a configuration file rather than being fixed only through preprocessor macros. The program can load the configuration when it starts, validate the values, and use them during billing.

This approach allows authorized tariff changes without recompiling the program.

13.4 Reading Storage

The system should store readings with the meter identifier, timestamp, and meter value. It should validate the readings, detect rollover where applicable, and preserve records for billing and auditing.

13.5 Validation and Reliability

The system should check missing readings, duplicate timestamps, invalid meter values, incorrect tariff configuration, and unexpected meter resets. Tests should include normal readings, peak-hour periods, rollover cases, and missing data.

13.6 Benefits

The proposed design supports more detailed consumption monitoring, peak-hour billing, configurable tariffs, improved record keeping, and future integration with automated billing systems.
